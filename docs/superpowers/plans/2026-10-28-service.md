# Dropvia public service implementation plan

**Goal:** Replace the preparatory screen with a bilingual, invitation-only file service website and the server contracts requested on 2026-10-28.

**Architecture:** FSD under `src/`: app owns Framework SSR, routes and providers; pages compose widgets/features/entities/shared. Server data starts in loaders, TanStack Query handles status polling, Router actions handle forms. No deployment, hooks or automatic commits. Execute autonomously in this session per the owner's instructions.

**Spec:** Latest user request, original `DESIGN.md`, confirmed English default/Russian and ordinary consumer audience. Baseline: `fdc7fb7`.

## Decisions and conflicts

- Request overrides the former coming-soon requirement and app-directory convention. Use `appDirectory: src/app`, keep SSR enabled.
- Interpret “react18n and i18n” as maintained `react-i18next` + `i18next`. URL is authoritative: English unprefixed, Russian `/ru`; real language links preserve page and hash. Request-scoped translation instances prevent leaks; no browser-only language detection or redirect.
- Request overrides the reference's dark-only advice. Preserve dark values and create semantic light equivalents using CSS `prefers-color-scheme`, without hydration scripts.
- Marketing describes storage/sharing purpose and invitation access. No fabricated customers, certifications, storage allowances, commercial prices, speed or SLA. Pricing uses invitation-based offers and comparison; amounts/limits are agreed before activation.
- Seven implemented documented API operations: upload POST403, download GET404, file metadata GET404, delete DELETE403, create share POST403, status GET200, access request POST201. Error envelopes and request IDs; methods restricted; private/error JSON no-store.
- Status snapshots: entire system healthy with probability89%; otherwise one component degraded. This is synthetic data, never a measured uptime percentage. Document implementation limitation internally, not as public marketing copy.
- Access endpoint validates bounded input, consent and origin. It acknowledges without persistent storage or email delivery as explicitly requested. Public success says await invitation; production integrations remain documented blockers.
- Legal text describes this invitation phase and actual site behavior. No invented legal entity, address, jurisdiction, provider, retention deadline or compliance claims. These particulars require owner/legal review before launch.
- Keep noindex until owner approves actual launch data; sitemap remains204. No concept/demo language on public pages.

## Review focus

1. Concurrent English/Russian SSR: no shared translation singleton, metadata and html lang agree.
2. Malformed JSON, oversized/chunked body, missing consent, foreign Origin, wrong methods: deterministic errors; no PII in response/logs/URL.
3. Status:89% whole snapshots healthy, initial data prevents immediate duplicate hydration request, polling stops hidden/offline/unmounted, failures retain last snapshot but visibly stale.
4. Form: pending/double submission,201 success,4xx/5xx/network errors, keyboard feedback and no-JS native submission.
5. Every route and theme: small screens, long Russian labels, preserved language destination, unknown route404, color contrast, reduced motion, SSR-visible main content.
